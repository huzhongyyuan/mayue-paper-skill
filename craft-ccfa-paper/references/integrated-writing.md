# 统一写作、改稿与研究组织

按当前任务读取本文件对应部分。通用层负责主张与证据、章节职责和审稿可理解性；Mayue 层在用户选择时提供具体的论证、模块和视觉组织案例。不要把三套技能的清单重复输出给用户。

## 从 idea 到可检验的方法

先从用户材料提取：要解决的任务、可用输入、输出、适用条件、主要比较对象、已知事实与未验证判断。生成控制类工作再明确「改变什么、保持什么、何时控制」；理论论文则明确对象、假设、结论和适用域，不能强行套控制任务。

把候选想法写为：在【条件】下，【现有假设／直接方案】受到【已验证问题或明确约束】限制；假设【机制】是原因；干预【变量】应使【可测信号】发生【预测】变化；因此采用【最小改动】，用【对照】区别于【替代解释】。没有诊断证据时保留“假设”，不要写成“我们观察到”。

最小实验要区分方法是否有效、解释是否成立、收益是否来自更多资源。相关工作验证覆盖新颖性所依赖的具体命题，元数据检索不能替代读原文。

Mayue profile 可参考 [idea-evidence](../modules/mayue/references/idea-evidence.md) 的诊断路径：Pose 的可获得监督拆分、Canvas 的独立难度因素、Emoji 的控制表示、Motion 的新骨干响应、FastVMT 的开销拆解、LiveLight 的在线操作时机。按问题选一种或少数适用路径，不要求一篇论文包含这些全部套路。

## 章节职责与可选的 Mayue 写法

下表是信息职责；篇幅、章节名称、合并与顺序由实际依赖和当前 venue 决定。完整通用细节见 [section-playbook](../modules/top-ml/references/section-playbook.md)；作者章节及段落图谱见 [writing-playbook](../modules/mayue/references/writing-playbook.md)。

| 章节 | 共用职责 | Mayue profile 的具体加法 |
|---|---|---|
| Title | 准确表达任务与区别，不用未证明的泛化词 | 用清晰任务词或控制接口形成记忆点；不为了模仿而强造 Follow-Your 名称 |
| Abstract | 任务→具体缺口→核心认识→机制→实际证据→范围 | 让每个机制回应前面的失败／约束；有数据才写诊断观察和提升幅度 |
| Introduction | 建立问题、比较轴、洞察和贡献证据 | 采用“直接方案为什么受限→最小改变→残留问题→配套机制”的链条，或与研究匹配的其他组织 |
| Related Work | 按机制、监督、成本或评价条件分组，公平定位 | 对照控制接口、表示或操作时机；Canvas 等案例中的比较维度应重新出现在实验中 |
| Formulation / Preliminaries | 定义输入输出、假设、符号、信息可得性 | 区分内容／身份／运动等改变项与不变量；说明训练和测试是否获得同一种控制信号 |
| Method overview | 一段可追踪的输入到输出路径，对应总图 | 先给阶段、分支或模块的职责图，再进入局部计算；保留真实并行关系 |
| 每个 Method 子节 | 解释必要性、计算、接口和技术后果 | 使用下述七项信息，借鉴 Pose/Emoji/Motion/Canvas 中与当前方法匹配的组织 |
| Training / Inference | 目标、更新对象、数据、执行路径和成本 | 明确冻结、训练、缓存、推理优化与更新时钟，避免 training-free 等词掩盖实际开销 |
| Theory（需要时） | 正式结论、假设、解释、适用范围、证明逻辑 | 保持理论自身结构；不能用视觉生成的叙事替代证明或添加伪定理 |
| Experiments | 设置、主比较、机制测试、消融、边界、实际成本 | 把“能控制、能保持、能泛化、付出什么代价”拆成可验证问题；不存在的测试不写成结果 |
| Discussion / Limitations | 条件→原因→后果→证据，界定中心主张 | 把遮挡、长序列、跨身份、在线延迟等实际失败条件与模块假设关联 |
| Conclusion | 回收洞察、证据与适用范围，不引入新结果 | 回到用户任务和已支持能力，避免把局部应用扩写成通用世界模型 |
| Appendix | 可复现细节、完整证明、补充结果与来源 | 补齐控制预处理、缓存设置、时间／裁剪协议；主结论不可完全依赖未呈现的关键证据 |

## 每个模块的七项信息

1. **Purpose**：解决哪个子问题，与中心主张有什么关系。
2. **Failure / cause**：直接方案的问题，或明确的设计约束；区分观察、推理、假设。
3. **Input**：输入及来源、符号／形状（仅保留有用信息）。
4. **Operation**：实际计算、公式／算法及非显然设计理由。
5. **Output / injection**：产出什么，交给谁，在哪层／时刻注入。
6. **State**：参数和缓存何时更新，训练与推理如何不同，是否推理优化。
7. **Verification**：哪个实验能支持或推翻它，或目前仍需哪项测试。

这是审阅信息的方式，不要求七句话、七段或七个标题。先解释数学式的用途与后果，再说明必要符号。正文名称、图中节点、公式和消融名一致；继承模块与新改动分别说明。

## 改稿时实际完成的工作

读取原段和必要上下文，先确定段落职责与科学含义；定位逻辑缺口、证据强度、术语不一致或冗余，再给修订后的正文／直接编辑源文件。保留数值、条件、引用键和符号；若确需修正，指明依据及影响。通常先修论证，再修句子。

有真实实验时围绕证据写；没有实验时可完成结构与方法草稿，把关键空缺标为 `[RESULT NEEDED]`、`[VERIFIED GAP NEEDED]` 等，不能填入看起来合理的结果。段落润色只报告会影响理解或结论的改动，避免强制生成整篇审稿表。

Mayue 的实际改稿流程与材料不足时的处理见 [revision-playbook](../modules/mayue/references/revision-playbook.md)。完整项目的记录结构见 [end-to-end-paper-workflow](end-to-end-paper-workflow.md)，已有项目不必迁移目录。

## 从文字衔接实验、图与版面

重要主张保持同一条链：问题／假设→方法操作→对应图节点→消融或检验→结果段→适用边界。必要时建立简洁账本：`claim | evidence or planned test | figure/table | section | scope | missing`。

整篇改写先按证据负担预算篇幅与首引位置，再做措辞压缩。当前会议规则优先于样本中位数；具体版式、浮动体与逐页检查使用 [manuscript-layout](manuscript-layout.md)。oral/highlight/spotlight 案例用于检查论点是否集中、证据是否清楚，不能当作录用公式。
